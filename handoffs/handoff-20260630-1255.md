## The plan for Phase A — DO NOT re-derive, read the ADR
**`docs/adr/0007-team-identity-via-fbref-id.md`** is the spec. Summary of the build steps (detail + rationale in the ADR):
1. **No migration** — `teams.fbref_id` column already exists (`unique=True` in the model) but is **unused (0 of 100 rows populated)**.
2. **Backfill `fbref_id` for the 100 existing teams from the *already-cached* FBref match pages** — zero network. The id is in each squad table's id attribute: `stats_<fbref_id>_summary` (visible in `parse_player_ids`' xpath today, and in pytest warnings e.g. `stats_d07537b9_summary`). Resolve each FBref name → canonical row via the existing `FBREF_TEAM_ALIASES` (already resolves all PL/Champ). Cache dir: `~/soccerdata/data/FBref/match_*.html` (huge; OneDrive makes `ls` crawl — glob/grep, don't `ls`).
3. **Name normalisation** — upgrade `ingestion/names.py::clean_name` (currently whitespace-only) to also fold accents + strip `FC`/`AFC`/club suffixes + lowercase, for the seam matcher only.
4. **Seam resolver** — resolve by source key first (`fbref_id` for FBref, `fdcouk_name` for fd.co.uk); on miss, **deterministic** link to an existing row by normalised-name **or explicit alias** (NO fuzzy/edit-distance — explicitly rejected); attach the missing handle rather than create a 2nd row. Switch `ingestion/players.py::resolve_fbref_team` to id-first, name/alias fallback, and capture `fbref_id` during ingest.
5. **Dup-guard report + test** — surfaces two rows sharing a normalised name, or an `fbref_id` row whose name matches an incoming fd.co.uk name. Mirrors ADR 0004's standing-regression-guard pattern.

**TDD it** (project rule for ingestion/reconciliation logic): the normaliser, the seam resolver, and the dup-guard get tests first. `test_reconciliation.py` already exists as the home for cross-source invariants.
