## URGENT — ESPN scoreboard: the date-range parameter is dead

**Every `upcoming` run has failed since 16/09 08:00** with `HTTP 400 Bad
Request`. Last success was 15/09 20:30. Measured this session, not inferred:

| request | result |
|---|---|
| `?dates=20260919` (single date) | **OK**, 5 events |
| no params at all | **OK**, 1 event |
| `?dates=20260919-20260920` (2 days) | **400** |
| `?dates=20260901-20260930` (30 days) | **400** |
| `?dates=20260817-20261031&limit=400` (the live window) | **400** |

So it is **not** a slug problem (all seven 400), not `limit`, and not a maximum
span — **any** `START-END` range is now rejected. `_SCOREBOARD_URL` in
`ingestion/upcoming.py` is built entirely around that form.

**Why it matters beyond a stale slate.** Per ADR 0014, `upcoming` is what marks
a league Fixture `finished`, and matchday's pending probe only counts finished
fixtures — so while this is broken the **FBref player pipeline silently stops
seeing new matches**. `squads` (09:00) also derives its club list from the
slate. The slate currently still holds scheduled fixtures to end-October, so
there is a little headroom, but it is not indefinite.

**Do not reach for the obvious fix without sizing it.** Iterating single dates
is 76 days × 7 competitions = ~532 requests per run, and `upcoming` runs up to
15×/day — roughly 8,000 requests/day against a source that currently costs 7.
That is a different relationship with ESPN than ADR 0009 signed up for. Worth
checking whether ESPN now wants a different parameter form before rewriting the
fetch loop.

This is a source changing shape, which `CLAUDE.md` says to **flag, not silently
work around**. It likely needs an ADR amending 0009.

## Things learned this session that are not in the code

- **A digest silence is not a green light.** `upcoming` showed no failures on
  07/09 because the 19:30 slot had not *run*, not because it had stopped being
  terminated. A missed slot leaves no start line at all; a terminated one leaves
  a start with no end. Different shapes, different causes.
- **`SetThreadExecutionState` is per-process**, so a short `run_backfill`
  invocation cannot clear the sleep block held by a long one. Running the
  zero-network repair alongside a live backfill is safe.
- **A running backfill has its modules already loaded**, so editing
  `ingestion/*.py` mid-run does not affect it — but the run will also not pick up
  a fix you just merged. That is why League Two Play-offs 2425 needed a manual
  repair pass after its stage.
- **Re-running a finished stage is safe and is now the repair command.**
  `run_backfill` prints `nothing pending — done` and then builds any missing team
  rows with zero network.
- **Test-suite timings are meaningless while a backfill runs** — one run hit the
  600s tool timeout purely on DB contention; the same suite takes ~50s on a quiet
  DB. Re-run before believing a slow or failed result.

## Standing gotchas (unchanged, still true)
- `&&` is a parse error in PowerShell 5.1 — use `;`.
- `pytest` piped to `tail` hangs — redirect to a file.
- `uvicorn --reload` and Vite HMR are unreliable under OneDrive.
- Repo-wide `grep` over the tree is slow enough to time out — use the Grep tool.
- MCP `postgres` points at the wrong DB — query via `backend/.venv` +
  `SessionLocal()`.
- Model column names are not what you would guess: `teams.canonical_name`,
  `players.canonical_name`, `competitions.name`; tables are `fixtures`,
  `team_match`, `player_match`.
- `backfill.log` lives at `backend/backfill.log`, **not** `backend/logs/`.
- `.gitignore` covers `*.log` but not `*.txt`.
